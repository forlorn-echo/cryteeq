## 1. User Story & Expected Behavior

**As an AI agent**, after applying the human's feedback to a file that still has an interrupted (in-progress) session, I re-run `cryteeq <file> --start-fresh` and get a brand-new review of the current on-disk content — the old session's snapshot and comments are permanently discarded, with no manual **Start Fresh** click needed in the UI.

**As a human reviewer**, when the agent launches me with `--start-fresh`, the UI opens on the file's current disk state with zero comments — exactly like the in-UI Start Fresh action (FR-2.9), performed at launch.

Without the flag, behavior is exactly FR-4.3 (resume in-progress, else new session). Exit codes, stdout purity, report format, API, DB schema, and UI are unchanged.

## 2. Functional Requirements

### 2.1 Start-fresh flag (FR-10)

| ID | Requirement |
|----|-------------|
| FR-10.1 | New boolean CLI flag `--start-fresh` (amends FR-1.2): `cryteeq [--port <n>] [--no-open] [--stdout] [--start-fresh] [--help] [--version] <file>`. Composable with every existing flag; usage-error and logging rules (FR-1.6) unchanged |
| FR-10.2 | With `--start-fresh`, session resolution (amends FR-4.3) is: load the file fresh from disk (validation per FR-1.3); then, if an in-progress session exists for the absolute path, discard it via the FR-2.9 restart transaction (delete in-progress row → cascade comments → create new session persisting the fresh snapshot); otherwise create a new session as today. Completed sessions are retained (FR-4.5) |
| FR-10.3 | Ordering: the existing in-progress session is only touched after the disk load succeeds — a validation failure (exit `1`) leaves it fully intact (still resumable) |
| FR-10.4 | Without the flag, session resolution is exactly FR-4.3 — unchanged |
| FR-10.5 | The stderr progress line reads `Review started fresh: <url>` when `--start-fresh` is passed (vs. `resumed`/`started`); all other stderr output is unchanged |
| FR-10.6 | Exit codes, stdout purity (FR-1.5), report format, API routes, DB schema, and UI are untouched; `restartReview` is reused as-is |

## 3. Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-11 | Session resolution is extracted from `cli.ts` into a dedicated module so the resume/fresh matrix is unit-testable without spawning processes (testing policy); the CLI keeps only flag parsing, error mapping, and wiring |
| NFR-12 | No new dependencies; no `console.*` calls; all non-report output on stderr |

## 4. Interface & Data Contracts

### 4.1 CLI

- Usage: `cryteeq [--port <n>] [--no-open] [--stdout] [--start-fresh] [--help] [--version] <file>`.

### 4.2 Session resolution module (`src/server/session.ts`)

```ts
export interface SessionResolution {
  review: ReviewRow;
  fileMeta: FileMeta;
  resumed: boolean; // in-progress row loaded from the DB (flag absent)
  fresh: boolean; // --start-fresh was passed
}

export async function resolveSession(
  db: DB,
  fileInput: string,
  absolutePath: string,
  startFresh: boolean,
): Promise<SessionResolution>;
```

- Resume path (in-progress row exists, flag absent): snapshot rebuilt from the DB row (`metaFromSnapshot` moves here from `cli.ts`), `resumed: true`.
- Fresh path (flag passed, or no in-progress row): `loadFile(fileInput)` — `FileError` propagates to the CLI; then `restartReview` when an in-progress row existed, `createReview` otherwise; `fresh` mirrors the flag.
- The CLI maps errors exactly as today: `FileError` → its message, anything else → `failed to load file: …` — stderr + `logError` + exit `1`.

### 4.3 Documentation

- `SKILL.md`: flags table gains `--start-fresh`; the re-review-cycle guidance and rules explain when agents pass it; exit codes unchanged.
- `README.md`: usage line, flags-table row, agent-workflow note.

## 5. Out of Scope (do not build)

- UI changes, `hash_changed` semantics, or prompts when the disk changed (FR-2.2 stays as-is)
- A runtime force-fresh API beyond the existing `POST /api/review/restart` (FR-2.9)
- Auto-detecting "file changed since last session → force fresh" — explicit flag only
