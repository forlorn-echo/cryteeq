## 1. User Story & Expected Behavior

**As an AI agent**, I run `cryteeq <file> --stdout` and block. If the human closes the browser tab instead of completing the review, the process stops itself within the heartbeat timeout window and exits `130` — the same interrupted/resumable contract as Ctrl+C — instead of hanging forever. stdout stays empty; I can prompt the human or re-run later to resume.

**As a human reviewer**, closing the tab ends the session cleanly: my comments are already saved, and re-running the command resumes them. A refresh (F5) or a second tab never kills the server while any tab is alive.

## 2. Functional Requirements

### 2.1 Heartbeat & watchdog (FR-11)

| ID | Requirement |
|----|-------------|
| FR-11.1 | The client pings `POST /api/heartbeat` immediately on mount and then every `HEARTBEAT_INTERVAL_MS` (5s), unconditionally (loading and error screens included). Ping failures are swallowed — a server that is already down (post-completion) is expected and must not surface in the UI |
| FR-11.2 | `POST /api/heartbeat` replies `200 {"ok": true}`, touches no database, and records the last-ping time on the server |
| FR-11.3 | The server runs a watchdog tick every `HEARTBEAT_CHECK_MS` (5s): if at least one ping has been received and none for more than `HEARTBEAT_TIMEOUT_MS` (30s), and completion has not started, it fires abandonment **once** (`onAbandoned`), then never again for the launch |
| FR-11.4 | The watchdog is **armed only by the first heartbeat** — a launch whose page is never opened (e.g. `--no-open` with no manual visit) runs until a signal, exactly as in v0.0 |
| FR-11.5 | On abandonment the CLI closes the server, writes `Page closed — comments are saved; re-run cryteeq to resume.` to stderr, and exits `130`. stdout stays empty (FR-1.5); the session remains in-progress and resumable; the §2.1 exit-`130` row's cause becomes "Interrupted (SIGINT/SIGTERM **or the page was closed**)" |
| FR-11.6 | Completion wins (mirrors FR-1.4 signal deferral): once report delivery has begun (`completionScheduled`), a stale or absent heartbeat can never trigger abandonment |
| FR-11.7 | Multi-tab semantics: any tab's ping refreshes the watchdog; the server stops only when **all** tabs stop pinging. A page refresh (a gap of a few seconds) must not trigger abandonment |
| FR-11.8 | Heartbeat constants live in `src/shared/heartbeat.ts` and are the single source of truth for both sides: `HEARTBEAT_INTERVAL_MS = 5000`, `HEARTBEAT_TIMEOUT_MS = 30000`, `HEARTBEAT_CHECK_MS = 5000`. `ServerDeps` accepts `heartbeatTimeoutMs`/`heartbeatCheckMs` overrides for tests |

## 3. Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-13 | No new dependencies; no `console.*` calls; the heartbeat route adds no request logging (FR-1.6 logging rules unchanged — abandonment itself is not logged to the launch log; it is a normal outcome, not a runtime error) |
| NFR-14 | The client scheduler is DOM-free and unit-testable via an injected fetch function; the server watchdog is testable via `ServerDeps` overrides with fake timers — no live servers, no port opens (testing policy) |
| NFR-15 | Known tradeoffs (accepted): browsers may throttle or suspend timers in long-hidden background tabs (Chrome's intensive throttling aligns wake-ups to ~once per minute) and during system sleep; in those states the watchdog may stop the server with `130` even though a tab technically remains open. Every such path is recoverable (comments saved, session resumable). Tuning is a constants change only |

## 4. Interface & Data Contracts

### 4.1 Shared constants (`src/shared/heartbeat.ts`)

```ts
export const HEARTBEAT_INTERVAL_MS = 5000;
export const HEARTBEAT_TIMEOUT_MS = 30000;
export const HEARTBEAT_CHECK_MS = 5000;
```

### 4.2 Server

- `ServerDeps` gains: `onAbandoned?: () => void`, `heartbeatTimeoutMs?: number`, `heartbeatCheckMs?: number` (defaults from §4.1).
- `POST /api/heartbeat` per FR-11.2.
- The watchdog `setInterval` is created in `buildServer`, fires per FR-11.3, and is cleared by an `onClose` hook so `app.close()` never leaks it.

### 4.3 Client (`src/client/heartbeat.ts`)

```ts
export type HeartbeatFetch = (
  url: string,
  init: { method: string },
) => Promise<unknown>;

export function startHeartbeat(
  fetchFn: HeartbeatFetch,
  intervalMs: number,
): () => void;
```

- Pings once immediately, then on the interval; returns a stop function; rejections are swallowed (FR-11.1). No DOM types — compiles under both tsconfigs.
- `App.tsx` starts it once on mount: `useEffect(() => startHeartbeat(fetch, HEARTBEAT_INTERVAL_MS), [])`.

### 4.4 CLI

- `onAbandoned` wiring: stderr line + `finish(130)` (existing idempotent shutdown path). No new flags; usage string unchanged; exit-code table updated per FR-11.5.

### 4.5 Documentation

- `SKILL.md`: exit-`130` row and rules updated (closing the tab stops the server after a short grace period; it does **not** complete the review); agent guidance for handling `130` after page-close.
- `README.md`: "How it works" + exit-codes note.

## 5. Out of Scope (do not build)

- WebSocket/SSE-based liveness (fetch heartbeat is dependency-free and proxy-friendly)
- A distinct exit code separating page-close from SIGINT (FR-11.5 reuses `130`)
- A pagehide/`sendBeacon` fast-path (a refresh also fires pagehide — indistinguishable; the timeout gap already covers it)
- CLI flags to tune heartbeat timings (constants change per NFR-15)
- Pausing the watchdog on `hash_changed` or during completion-dialog display

## 6. Acceptance Criteria

| # | Criterion | Covers | Verified by |
